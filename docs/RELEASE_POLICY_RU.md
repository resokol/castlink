# Релизы CastLink

Исходники, актуальные сборки и инструкции находятся в единственном публичном `resokol/castlink`. Прежнее имя `resokol/castlink-releases` перенаправляет в него и сохраняет совместимость старых ссылок. [Правила выпуска](../distribution/RELEASE_POLICY.md).

## Источник версии

Для обычной web/development-сборки источник **семантической версии** — поле `version` в корневом `package.json`. При сборке серверного пакета выбранное направление задаёт `CASTLINK_PRODUCT_VERSION` / `CASTLINK_PRODUCT_BUILD_NUMBER`; эти значения попадают в Next.js через Docker build args без изменения исходников.

Версии поставляемых пакетов независимы и находятся в `distribution/release-tracks.json`: `client`, `server-setup`, `linux`. В конфигурации назначены ветки `release/client`, `release/server-setup`, `release/linux`; перед сборкой проверяют их фактическое наличие и source SHA, `main` остаётся интеграционной. Повышается только версия обновлённого направления. Конкретные опубликованные сборки и теги перечислены в [выборе продуктов](../distribution/PRODUCTS.md). Порядок ветвления, сборки и публикации описан в [инструкции деплоя](PRODUCTION_DEPLOYMENT_RU.md#три-независимых-направления-выпуска).

Формат: SemVer (`MAJOR.MINOR.PATCH`), например `0.9.29`.

`apps/web/package.json` намеренно не содержит собственного `version`, чтобы версия продукта не дублировалась в двух местах.

## Версия продукта и идентификатор сборки

Это разные значения:

- **productVersion** — версия выбранного направления при сборке пакета, иначе корневого `package.json`;
- **buildId** — идентификатор конкретной сборки/развёртывания;
- поле **version** в `/api/version` временно остаётся алиасом `buildId` для обратной совместимости с существующим механизмом проверки обновлений.

При production-сборке `buildId` задаётся через `STUDIOLINK_RELEASE`. Если переменная не задана, локальная сборка получает уникальный development build id.

Рекомендуемый production build id:

```
<productVersion>-<short-git-sha>
```

Например:

```
1.0.0-a1b2c3d
```

## API версии

`GET /api/version` возвращает:

```json
{
  "version": "1.0.0-a1b2c3d",
  "buildId": "1.0.0-a1b2c3d",
  "productVersion": "1.0.0"
}
```

`version` нельзя удалять до отдельной миграции клиентов.

## Правила релиза

1. Изменения проходят через отдельную ветку/PR.
2. CI обязан пройти: frozen install, TypeScript, стабильные тесты, production build.
3. Перед релизом обновляются версия выбранного направления и его пользовательские примечания. Корневая версия меняется только при обновлении web/runtime.
4. Production image собирается из конкретного commit SHA с явным `STUDIOLINK_RELEASE`.
5. После проверки создаётся точный тег `<track>-v<version>-<12-char-sha>`; направления выпускаются отдельно. Старые готовые теги сохраняются.
6. GitHub commit сам по себе не является деплоем.
7. Нельзя помечать релиз проверенным, пока production build не был реально проверен владельцем.

## Тесты CI

`pnpm test:ci` запускает только автономные тесты, которые не требуют отдельного Next.js процесса или LiveKit.

Интеграционные API-тесты, которым нужен изолированный сервер на `127.0.0.1:3001`, не входят в быстрый CI этого этапа. Их нельзя запускать против production.

Также пока отдельно остаются старые test harness-ограничения, связанные с разрешением alias-импортов в некоторых component-тестах. Они должны исправляться отдельной задачей, а не маскироваться в CI.

## Назначение публикации

В ручных workflow публикация выключена по умолчанию (`publish=false`). Только явное `publish=true` после проверки включает публикацию. Workflow и локальный publisher используют единственный `resokol/castlink`; отдельного назначения primary/public нет. Точные теги сохраняют source SHA выпуска, даже когда релизные ветки переходят на следующий проверенный commit. Ранее выпущенные архивы не пересобираются ради переименования репозитория или обновления документации.
