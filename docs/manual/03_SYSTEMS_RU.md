# 03. Системы, модули и связи

[Оглавление](../MANUAL_RU.md) · [Интерфейсы](02_INTERFACES_RU.md) · [Далее: данные и доступ](04_DATA_ACCESS_RU.md)

## Два контура вместо одной «видеопрограммы»

```text
Браузер ── HTTPS-команды ── Next.js API ── PostgreSQL / runtime state
   │                              │
   │                              └── LiveKit server API: управление комнатой
   └── WebRTC-аудио/видео ──────── LiveKit SFU ─────── другие браузеры / output
                                     │
                                     └── TURN при необходимости сетевого реле
```

Верхний путь — **control plane**, управление. Нижний — **media path**, передача медиа. База данных не получает каждый видеокадр. PostgreSQL сохраняет комнаты, права и размещение; LiveKit пересылает медиапотоки. Поэтому исправление SQL-миграции не требует перезапуска медиасервера.

Однако «БД не в media path» не означает «БД ни на что не влияет». Без неё могут перестать работать новый вход, выдача прав и команды. Сильная нагрузка на том же физическом сервере способна косвенно влиять на медиа через CPU, память или сеть. Этого нельзя исключить одним утверждением о разделении модулей.

## 1. Web-приложение

Next.js объединяет серверные маршруты и React-страницы. Файлы `app/.../page.tsx` описывают страницы; `app/api/.../route.ts` — HTTP API; `app/v1/.../route.ts` — межсерверные маршруты. `app/layout.tsx` подключает общие стили, метаданные и уведомление о версии.

Код с `"use client"` работает с браузерным состоянием и событиями. Серверный обработчик не должен обращаться к `document`, а браузерный компонент не должен получать пароль PostgreSQL. Это практическая граница, а не только соглашение о названиях папок.

`next.config.ts` проверяет версию продукта, формирует build ID и задаёт защитные HTTP-заголовки. `instrumentation.ts` проверяет постоянное хранилище и backend комнат при запуске Node-runtime. Сейчас эта startup-проверка **не заменяет** проверку всех control-plane миграций.

Исходники: [layout](../../apps/web/app/layout.tsx), [конфигурация](../../apps/web/next.config.ts), [startup](../../apps/web/instrumentation.ts).

## 2. Компоненты интерфейса

Большая страница Studio не должна быть местом для любой новой функции. Отдельные блоки уже выделены в компоненты: управление комнатами, устройства, публикация возврата, статистика возврата, гости, персонал и перенос сервера.

Например, `GuestVideoCard` отвечает за представление карточки и вызывает переданные обработчики. Он не должен самостоятельно выбирать чужую комнату в БД. `RemoteVideoPreview` подключает принятый видеотрек к HTML `<video>`. `useVideoRotation` занимается его отображением. Это три разные ответственности.

Общие `MonitoringControls` используются для личного прослушивания. `TalkbackControls` управляет служебной голосовой связью и отдельными публикациями персонала. `MediaDevicePicker` перечисляет устройства браузера. `RoomConference` собирает видеосетку и footer гостевой конференции.

CSS тоже разделён. `globals.css` содержит общий визуальный язык и стили LiveKit-обёрток. CSS Modules, например `StudioEntry.module.css`, применяются локально к конкретным экранам. Правка глобального селектора `button` может случайно изменить все страницы; правка небольшого scoped-класса обычно безопаснее.

## 3. Захват → публикация → подписка → отображение

Сначала браузер захватывает устройство. Затем LiveKit-клиент публикует track. Другие клиенты подписываются на него и прикрепляют к своему `<video>` или аудиовыходу. Название участника, источник камеры и технический track ID — не одно и то же.

Путь гостевой камеры:

```text
GuestAccessGate → GuestAvCheck → RoomConnector
  → разрешение браузера / LocalVideoTrack
  → LiveKit publish
  → удалённый TrackSubscribed
  → RemoteVideoPreview → useVideoRotation → video-fit
```

Подмена CSS не исправит ошибку захвата камеры. Изменение параметров захвата не исправит перекрывающий видео toolbar. Для диагностики сначала определите, на каком этапе пропадает правильный кадр.

В новой геометрии `video-fit.ts` рассчитывает вписывание по четырём размерам: ширина/высота источника и ширина/высота контейнера. При 90/270° меняются местами размеры видимого прямоугольника. Это позволяет сохранить весь кадр без искусственного растяжения.

## 4. LiveKit и транспорт

LiveKit здесь выступает SFU — сервером пересылки потоков. Он не является страницей Studio и не хранит все продуктовые права CastLink. Приложение выдаёт ограниченный LiveKit JWT, а медиасервер проверяет разрешение подключаться, публиковать и подписываться.

Для медиа предпочтителен подходящий прямой сетевой маршрут браузера к ноде. ICE выбирает маршрут; STUN помогает определить сетевое окружение; TURN может передавать трафик через реле, если обычный путь не работает. Наличие белого IP у сервера не отменяет настройку firewall и портов.

Caddy обслуживает HTTPS и проксирование web/signaling. HAProxy в текущем TURN/TLS-сценарии распределяет TLS-трафик по SNI. Это не причина направлять RTP-видео через Next.js API. Согласованность PROXY protocol на обеих сторонах описана в [TURN/TLS](../TURN_TLS_RU.md); его нельзя включать только на одной стороне.

Фактические порты и адреса берутся из конфигурации установки, а не из универсального списка из интернета. Смотрите [LiveKit infra](../../infrastructure/livekit/docker-compose.yml), [production media compose](../../infrastructure/production/docker-compose.media.yml), [HAProxy](../../infrastructure/haproxy/haproxy.cfg).

## 5. Качество и simulcast

Simulcast позволяет отправлять несколько вариантов одного видео. Получатель может выбрать слой, подходящий своему размеру окна и сети. Поэтому выбор слоя и ограничение суммарной отправки — разные операции.

`video-quality.ts` содержит допустимые FPS, диапазоны битрейта, параметры публикации и распределение общего бюджета между RTP encodings. `guest-video-bitrate.ts` применяет этот механизм к камере гостя и повторно проверяет параметры после reconnect, republish и изменения metadata.

Команда нового лимита проходит так:

```text
GuestVideoCard → Studio handler → POST /api/participants (video-bitrate)
  → серверная проверка studio/room/role
  → metadata гостя: videoMaxBitrateKbps
  → событие LiveKit у гостя
  → RTCRtpSender.setParameters
```

Команда не передаёт права публикации и не меняет microphone/screen-share bitrate. Если браузер не применил параметры, нужно сообщить об ошибке, а не рисовать целевое число как фактический поток. Принимать лимит нужно по измерениям после переходного периода, с учётом направления и источника.

## 6. Studio Return и право основной студии

`studio-control.ts` хранит `primaryClientId`, `leaseUntil`, `epoch`, `desired`, `actual`, `revision`. Это не SQL-комната и не LiveKit participant: это состояние управления эфиром.

`primaryClientId` указывает, кто сейчас является основной студией. Lease продлевается heartbeat. `epoch` меняется при смене поколения основной студии; старая команда с прежним epoch не должна управлять новым эфиром. `revision` задаёт порядок изменения настроек внутри поколения.

`desired` — что оператор попросил сделать. `actual` — что клиент реально подтвердил или измерил. Успешный запрос команды не равен успешно включившемуся физическому устройству. Поэтому UI показывает переходные/ошибочные состояния отдельно.

`StudioReturnPublishingControls` управляет кнопками публикации, `StudioReturnStatsPanel` показывает измерения, `studio-outbound-stats.ts` выбирает достоверный для данного контекста источник данных. `studio-room-lifecycle.ts` и `studio-video-recovery.ts` связывают события восстановления.

Основная студия не должна терять роль от того, что второй администратор открыл панель. Принудительный захват/перенос — отдельное решение, а не побочный эффект рендера страницы.

## 7. Личный звук и аудиометр

`personal-monitoring.ts` хранит локальные предпочтения потребления. `monitor-audio.ts` связывает их с аудиоэлементами и обработкой жизненного цикла. Это не изменение общей публикации гостя.

Анализатор GuestAudioMeter читает отдельную ветвь того же принятого аудиотрека. Ветка заканчивается нулевым GainNode, чтобы измерение не добавляло второе слышимое воспроизведение. При закрытии индикатора отключаются его узлы и контекст, но не останавливается исходный remote track.

`audio-meter.ts` содержит математическую часть измерения и плавность индикатора. Изменение зависимостей React-эффекта не должно пересоздавать контекст каждые две секунды вместе со статистикой. Измерение тишины, медийный mute и запрет autoplay — отдельные случаи.

## 8. Комнаты и их постоянное хранилище

`room-store.ts` — общий интерфейс чтения и изменения комнат. `postgres-room-store.ts` — его PostgreSQL-реализация. JSON backend остаётся отдельным явно выбранным режимом; аварийное молчаливое переключение между двумя источниками данных недопустимо.

Публичные API комнат не должны напрямую собирать SQL по строкам браузера. Параметры запроса отделяются от SQL, изменения выполняются транзакционно, studio scope должен учитываться на каждом переходе.

Подробная карта таблиц и файлов находится в следующей главе. Важно: переход на БД не означает, что из проекта исчезли все JSON-файлы. Studio control, некоторые access/runtime состояния и статистика всё ещё имеют файловые хранилища.

## 9. Control plane и multi-tenant

Tenant — независимый пользовательский контекст. Иерархия данных: Account → Organization → Studio → Room → Participant. Нода — физический ресурс; одна нода может обслуживать несколько студий.

`tenant-scope.ts` и `studio-scope.ts` проверяют идентификаторы и строят namespace. `control-plane-store.ts` читает реестр нод/студий и выполняет placement. `control-plane-client.ts` позволяет удалённой ноде читать разрешённую информацию через подписанный HTTPS вместо прямого подключения к центральной БД.

Наличие таблицы accounts не означает, что в этом релизе есть полный пользовательский account-login, биллинг и личный кабинет. Owner-ссылки — текущий рабочий механизм доступа к отдельным студиям, а не завершённая коммерческая IAM-платформа.

## 10. Scheduler и состояния ноды

`node-scheduler.ts` выбирает подходящую ноду по режиму, health, свежести heartbeat и capacity. Если свободной мощности нет, честный ответ — отказ/ожидание, а не молчаливое переполнение.

| Режим | Назначение |
|---|---|
| Enabled (`active`) | Нода разрешена для новых назначений при хорошем health/capacity |
| Draining | Новые назначения блокируются; это штатный путь вывода из работы |
| Disabled | Нода административно исключена из выбора |
| Force Offline (`force_offline`) | Аварийное логическое исключение; требуется подтверждение |

Административный режим и наблюдаемое здоровье — разные поля. Heartbeat не должен отменять ручной Disabled. Force Offline не является командой `shutdown` ОС и не гарантирует бесшовный перенос медиа. Проверку сохранения существующих сеансов и поведения reconnect выполняют на реальном стенде.

## 11. Heartbeat и topology

Heartbeat — короткий подписанный отчёт ноды о себе. `node-heartbeat.ts` проверяет форму, время и подпись, `node-heartbeat-auth.ts` находит серверный секрет, `scripts/node-heartbeat.mjs` собирает и отправляет данные. В Linux его может запускать systemd timer; контейнерный запуск — отдельная конфигурация установки.

Topology — более подробный снимок комнат и публикаций. `node-topology.ts` объединяет node-local inventory с активными LiveKit-комнатами. `platform-topology.ts` сопоставляет это с центральным реестром. Поэтому новая комната, ещё не попавшая в центральный список, не исчезает из диагностики.

Нельзя показывать «0 участников», если нода не ответила. Нельзя молча переписывать routing по наблюдению. В UI раздельно показаны назначение из БД, ноды наблюдения, свежесть снимка и неизвестные значения.

В текущем heartbeat `cpuLoad` вычисляется из нормализованного load average, а не из измеренного процента занятости CPU. Network out может отсутствовать в payload; тогда нужен прочерк. Отдельно считаете людей, технические подключения и видеопубликации — это разные числа.

## 12. Перенос и восстановление

`client-transfer.ts` хранит браузерный snapshot перехода. `server-transfer.ts` работает с целевыми origin, билетами и межсерверным доверием. `/api/server-transfer` и `/v1/control/studio-transfer` выполняют серверную часть. `/transfer` принимает клиента на целевой стороне.

Билет ограничен ролью, студией/комнатой, сроком и доверенной целевой стороной. Перенос не должен переносить чужие права между tenant-ами. Забытый `studioId` здесь опаснее косметического дефекта.

`reconnect-status.ts` описывает состояния восстановления интерфейса. Восстановление трека, повторное подключение комнаты и смена физического сервера — разные сценарии. Нельзя заменять их принудительным обновлением вкладки в эфире.

## 13. Статистика и отчёт

`rtc-telemetry.ts` читает WebRTC stats и вычисляет изменения счётчиков. Первый замер и сброшенный счётчик не превращаются в отрицательный или огромный выдуманный битрейт.

`/api/stats` проверяет токен/identity/room и ограничения payload. `telemetry-store.ts` пишет историю в JSONL, ограничивает срок/размер и агрегирует интервалы. `telemetry-types.ts` задаёт структуру данных и функции суммирования/средних. `StatisticsDashboard` строит экран, `stats-csv.ts` экранирует CSV, `stats-report.ts` строит автономный HTML с экранированием строк.

Фильтры должны применяться согласованно к графикам, списку сессий и экспорту. Историю по времени не стоит подменять только последним snapshot участника. В этой версии таблица последних потоков и временной график агрегатов — разные уровни детализации; полного архива каждого RTP-пакета нет.

## 14. Setup, лицензирование и server registry

`setup-state.ts` и `license-activation.ts` организуют первый setup и обмен с внешним сервисом активации. `license.ts`, `server-lease.ts` проверяют подписанные документы. `license-state.ts` хранит runtime-состояние; `entitlement.ts` решает, разрешена ли операция при выбранном режиме enforcement.

Это инфраструктурная основа, а не доказательство, что коммерческий License Service уже развёрнут. SQL в `infrastructure/license-service` — отдельная схема реестра, не замена `castlink_control.nodes`. Бесплатную модель сервиса нельзя выводить из названия файла license: смотрите реальную конфигурацию и продуктовые правила.

`server-registry-client.ts` обращается к внешнему backend. Поэтому `/servers` может сообщать об отсутствии backend, даже когда медиа и локальные ноды работают. Такой отказ не следует исправлять перезапуском LiveKit.

## 15. Нативные приложения, инструменты и CI

`apps/studio-linux` — bootstrap-заготовка, печатающая сообщение. `apps/studio-windows` — начальный Win32/CMake-клиент; его README описывает будущие этапы подключения LiveKit/WASAPI. Это не равнозначная замена действующему браузерному Studio.

Конфигурация редактора и локальные инструменты разработки не являются серверными access policy. Технические ограничения приложения описаны в `docs/CRITICAL_INVARIANTS_RU.md`.

GitHub Actions выполняет TypeScript, тесты, PostgreSQL integration и сборку. Workflow образа публикует Docker image, но сам по себе не выполняет production deploy. Конкретные команды и порядок работы разобраны в главах 05–06.
