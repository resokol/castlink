# 04. Данные, роли и безопасность

[Оглавление](../MANUAL_RU.md) · [Системы](03_SYSTEMS_RU.md) · [Далее: разработка](05_DEVELOPMENT_RU.md)

## Что такое БД в этом проекте

PostgreSQL хранит таблицы. Таблица похожа на строго организованную ведомость: у каждой строки есть поля определённых типов, ключи и ограничения. SQL — язык запросов к этой ведомости. Имя схемы перед точкой разделяет группы таблиц: `castlink_control.nodes` — таблица `nodes` в схеме `castlink_control`.

Запрос `SELECT` читает данные. `INSERT` добавляет, `UPDATE` изменяет, `DELETE` удаляет. `CREATE TABLE` и `ALTER TABLE` меняют структуру. Эти команды не следует выполнять в production «для проверки», если не понятно, к какой БД подключена консоль.

**Транзакция** объединяет изменения в одну операцию. `COMMIT` подтверждает её, `ROLLBACK` отменяет. Но откат транзакции не откатывает отправленный HTTP-запрос, файл на другом компьютере или уже опубликованное видео.

## Три разных вида хранения

| Хранилище | Что в нём находится | Где смотреть реализацию |
|---|---|---|
| Node-local PostgreSQL | Комнаты конкретной установки и студии, пароли/версии доступа и настройки комнаты | `postgres-room-store.ts`, `infrastructure/postgres` |
| Central control plane | Реестр нод, организаций/студий, назначения и доступ Super Admin | `control-plane-store.ts`, `infrastructure/control-plane` |
| Файлы постоянных данных | Installation identity, Studio control, некоторые runtime/access состояния, JSONL-статистика | `persistent-storage.ts`, `studio-control.ts`, `telemetry-store.ts` |

Они могут физически находиться на одном VPS, но решают разные задачи. Наличие PostgreSQL не означает, что папку `/data` теперь можно удалить. Копия только БД не заменяет backup файлового состояния, и наоборот.

## Таблицы node-local storage

`castlink_rooms` содержит комнаты. Главный контекст — `installation_id + studio_id + name`. Поэтому `interview` в Studio A не совпадает с `interview` в Studio B. `castlink_installations` и `castlink_schema_migrations` помогают проверять установку и схему хранения.

Поля паролей и версий доступа не являются обычной диагностикой. Хэш пароля применяется для проверки, зашифрованное значение может использоваться там, где разрешённому оператору нужно увидеть текущий пароль. Публичному пользователю такие поля не возвращаются целой строкой БД.

`room-store.ts` скрывает подробности backend от API. При `CASTLINK_STORAGE_BACKEND=postgres` ошибка SQL не должна превращаться в чтение случайного старого JSON. Иначе два оператора увидят разные комнаты и разные права.

## Центральная схема

| Таблица | Смысл |
|---|---|
| `accounts` | Основа идентичности учётной записи; не доказательство готового account-login UI |
| `organizations` | Организации — будущая/текущая группа владения студиями |
| `organization_members` | Связь учётных записей и организаций |
| `studios` | Студии, их owner access version и назначение ноды |
| `rooms` | Центральный реестр комнат; может отставать от node-local inventory |
| `nodes` | Физические ноды, административное состояние, health, capacity, heartbeat |
| `platform_access` | Версии отзыва доступа платформы; новая модель использует ключ `super_admin_v2` |
| `platform_credentials` | Хэши одноразовых приглашений и сессий Super Admin, сроки и признак использования |

Не исправляйте несовпадение реестра и живой ноды удалением «лишних» комнат. Комната может быть действующей на ноде, пока центральный metadata-реестр ещё не обновлён. Диагностика специально объединяет эти источники, не меняя их молча.

## Файловое состояние

`STUDIOLINK_DATA_DIR` задаёт корень постоянных данных. `installation.json` хранит identity установки; `runtime/` содержит служебные JSON; `stats/` — измерения. Имена и overrides видны в `persistent-storage.ts` и каталоге исходников.

Studio control хранит lease/epoch/desired/actual в `studiolink-studio-control.json`. Модераторский access backend имеет собственный runtime-файл. Телеметрия группируется по комнате и часовым JSONL-файлам. Это намеренное разделение, а не незавершённость миграции каждой строки в PostgreSQL.

`atomicWriteJson` записывает временный файл и заменяет им основной. Это уменьшает риск частичной записи, но не создаёт распределённую транзакцию между несколькими web-процессами. Текущую схему нельзя без проверки превратить в несколько реплик с общей файловой папкой.

## Почему миграция обязательна

Миграция — исполняемое изменение структуры данных, связанное с новой версией кода. Когда новый код обращается к `platform_access`, а таблица не создана, возникает `relation ... does not exist`. Перезапуск приложения не создаёт таблицу сам собой.

В control plane файлы идут по порядку: `001_multitenant.sql`, `002_super_admin.sql`, `003_node_operational_state.sql`, `004_platform_credentials.sql`. Новый доступ Super Admin требует 004. Скрипт `control-plane-migrate.mjs` читает SQL-файлы и выполняет их транзакционно по файлам. Не считайте запуск старой копии скрипта гарантией, что новые SQL-файлы вообще присутствуют рядом с ним.

В текущем production update нет универсального доказательства, что все новые таблицы уже созданы. Поэтому новая миграция проверяется отдельным release gate **до** включения зависящего от неё кода. Backup, совместимость старой версии и план rollback — обязательные части этого решения.

## Роли: внешний вид не даёт прав

| Доступ | Что он означает | Чего он не даёт автоматически |
|---|---|---|
| Гость | Участие в разрешённой комнате | Просмотр чужой студии, административные API |
| Модератор | Разрешённые действия в своей комнате/студии | Владение всей платформой, Super Admin |
| Администратор комнаты | Расширенное управление конкретной комнатой | Захват основной студии, глобальная диагностика |
| Studio owner | Управление конкретной Studio | Владение другими Studio, доступ Super Admin |
| Legacy Studio password | Совместимость входа в default Studio | Глобальное повышение до Super Admin |
| Super Admin | Управление платформой и диагностикой через отдельную сессию | LiveKit publication grants только по наличию этой cookie |
| Технический output/monitor/watch | Получение разрешённого сигнала | Публикация камеры и служебные права человека |

`identity`, metadata роли и scope проверяются серверно. Имя «Администратор», цвет бейджа или значение `role` в ручном запросе не должны давать права. UI gate нужен для удобства; серверный guard — для защиты.

В новой границе `/api/studios`, `/api/servers` и выдача/отзыв Studio owner-ссылок также требуют Super Admin. Иначе запрет одной страницы оставил бы обход через старый глобальный API.

## Три класса токенов

**LiveKit JWT** разрешает медийное подключение с определёнными grants. Он не является паролем PostgreSQL и не должен автоматически давать доступ ко всей платформе.

**Подписанные scoped-приглашения CastLink** используются для существующих guest/studio/admin/moderator/viewer сценариев. Их подпись, scope, срок и access version проверяются на сервере. Они могут быть отозваны изменением соответствующей версии.

**Новые opaque credentials Super Admin** — случайные значения `csa2.…`, а не клиентские утверждения о роли. В БД хранится только SHA-256-хэш. Сервер проверяет существование записи, тип, срок, использование и текущую версию доступа. Знание обычного подписывающего секрета приглашений не превращает произвольную строку в такую запись.

## Доступ владельца сервиса и делегирование

Первое приглашение создаётся **только в консоли сервера** командой `scripts/super-admin-owner.mjs`. У HTTP API нет разрешённого bootstrap через Studio. Команда пишет ссылку в новый закрытый файл, а не печатает её в CI/logs.

Приглашение живёт 15 минут и применяется один раз. Обмен выполняется транзакционно: два одновременных запроса не должны оба войти по одному приглашению. После обмена браузер получает отдельную HttpOnly/Secure/SameSite-сессию до 12 часов. Фрагмент ссылки удаляется из адресной строки.

Уже допущенный Super Admin может выдать отдельное приглашение. Выход отзывает текущую сессию в БД, а не только удаляет cookie. Глобальный отзыв меняет версию и отменяет ранее выданные приглашения и сессии. Восстановление после глобального отзыва доступно владельцу сервера через консоль.

Старые bootstrap-ссылки и cookie `castlink-super-admin` новая модель не принимает. Миграция требует заранее сохранить владельцу рабочий серверный доступ. Сам Super Admin не подключается как скрытый публикующий участник комнаты.

Это не полноценная корпоративная IAM: здесь ещё нет UI именованных сотрудников с отдельными политиками, MFA и индивидуальным отзывом всех сессий конкретного сотрудника. Эти возможности нельзя подразумевать только по слову «Super Admin».

## Секреты и безопасная диагностика

Реальные `web.env`, `postgres.env`, SSH private keys, registry tokens и приглашения не коммитят в Git. `NEXT_PUBLIC_*` означает потенциальное попадание значения в браузерную сборку; это не место для секретов.

Не публикуйте полный `docker inspect ... Config.Env`, дамп БД или HAR-файл без очистки. Для диагностики достаточно сначала версии, кодов ответа, request ID, доступных счётчиков и времени ошибки. Логи могут содержать идентификаторы и другие рабочие данные, даже если паролей там нет.

URL со `#access`, `#owner`, приглашением или viewer grant — это доступ. Не вставляйте такой URL в публичную issue. Используйте отдельно выдаваемые доступы и отзывайте их после теста.

## Anti-abuse и его пределы

`rate-limit.ts` ограничивает частоту control-plane запросов и возвращает `429` с `Retry-After`. Это полезно против массовой выдачи токенов/команд, но не защищает узкий интернет-канал от объёмной DDoS-атаки.

Счётчики этой реализации находятся в памяти процесса. После перезапуска они сбрасываются, а при нескольких репликах не становятся общими автоматически. Заголовки адреса клиента требуют корректной доверенной proxy-цепочки. Нельзя обещать защиту от подмены IP без проверки ingress.

Ни этот limiter, ни новая авторизация не должны вставляться в RTP/UDP-тракт. Тем не менее отсутствие прямой обработки медиа не заменяет нагрузочное измерение и тест reconnect под ограничениями.

## Откат версии — тоже решение по безопасности

Откат на старый образ может вернуть старый bootstrap и старые правила доступа. Поэтому после перехода на creator-only модель нельзя считать любой предыдущий образ безопасным rollback. Нужно либо сохранить новую границу доступа, либо временно закрыть чувствительные платформенные endpoints до исправления. Возврат старой БД поверх новой — отдельная, потенциально разрушительная операция.
