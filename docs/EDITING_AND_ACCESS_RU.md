# VS Code локально + GitHub

## Открыть проект

На компьютере Linux:

```bash
cd ~/studiolink
code studiolink.code-workspace
```

Если `code` отсутствует в PATH после установки в домашний каталог:

```bash
~/.local/bin/code ~/studiolink/studiolink.code-workspace
```

В VS Code подтвердите доверие своему проекту. Откройте `README.md`, нажмите Ctrl+Shift+V для удобного просмотра Markdown. Ctrl+P ищет файл, Ctrl+Shift+F ищет текст во всём проекте, Ctrl+Shift+G показывает изменения Git. Терминал открывается через меню «Терминал → Создать терминал». Сохранение — Ctrl+S.

В «Терминал → Запустить задачу» подготовлены четыре команды: разработка, проверка TypeScript, сборка, запуск сборки. Разработка и запуск сборки занимают один порт 3000: сначала остановите предыдущую задачу через Ctrl+C. Задачи запускают сайт только на `127.0.0.1`; адрес в браузере — `http://localhost:3000/studio`.

VS Code можно установить из официального пакета для Linux: [инструкция Microsoft](https://code.visualstudio.com/docs/setup/linux). Для установки из tar.gz в домашний каталог системный apt не будет автоматически обновлять редактор; новый архив устанавливается отдельно. Это не связано с обновлением StudioLink.

## Подключить GitHub

Репозиторий: [resokol/studiolink](https://github.com/resokol/studiolink). Чтение публичного репозитория не требует входа. Для отправки изменений нужен ваш аккаунт с правом записи.

1. В VS Code откройте расширения Ctrl+Shift+X и при необходимости установите рекомендованное **GitHub Pull Requests and Issues** (`GitHub.vscode-pull-request-github`).
2. Откройте раздел GitHub этого расширения и выберите вход. VS Code откроет браузер для авторизации. Войти и подтвердить доступ нужно лично в браузере; пароль не вводится в исходники или терминальные команды.
3. В Source Control проверьте текущий репозиторий и изменения. При первой отправке через HTTPS редактор может ещё раз предложить авторизацию Git.
4. Проверка чтения: `git ls-remote origin HEAD` выводит SHA и `HEAD`. Это подтверждает связь, но не право записи. Право записи подтверждается успешным push вашей ветки.

Подключение GitHub в Codex и авторизация Git в локальном VS Code — разные подключения. Работа первого не доказывает готовность второго. Подробности: [GitHub в VS Code](https://code.visualstudio.com/docs/sourcecontrol/github).

Быстро почитать/поправить файлы можно и через [github.dev](https://github.dev/resokol/studiolink). Это запасной браузерный редактор; для запуска приложения используйте локальный VS Code. [Ограничения github.dev](https://docs.github.com/en/codespaces/the-githubdev-web-based-editor).

## Безопасный цикл небольшой правки

Команды выполняются в `~/studiolink`. Перед правкой:

```bash
git status --short
git diff -- apps/web/app/studio/page.tsx apps/web/lib/video-quality.ts
git switch -c fix/my-change
```

Используйте новое понятное имя ветки. На момент подготовки гайда два указанных файла уже содержали ручные правки: новая ветка перенесёт их с собой, а не отделит автоматически. Сначала разберитесь с ними; не нажимайте «Discard all» и не выполняйте `git reset --hard`.

Измените одну функцию или один стиль, сохраните, проверьте страницу. Запустите проверку TypeScript и подходящие тесты из [диагностики](TROUBLESHOOTING_RU.md). Затем посмотрите разницу:

```bash
git diff --check
git diff -- apps/web/app/globals.css
```

Пример сохранения только изменения дизайна (выполнять, только если действительно правили этот файл):

```bash
git add apps/web/app/globals.css
git diff --cached
git commit -m "Adjust video layout on small screens"
git push -u origin HEAD
```

`git diff --cached` показывает именно то, что войдёт в коммит. Не используйте без просмотра `git add .`: туда могут попасть чужие незавершённые правки. После push откройте GitHub и создайте Pull Request в main. В описании укажите, что изменилось и какие проверки выполнены. Слияние сохраняет изменение в основной ветке, но не обновляет VPS.

Перед получением новых изменений проверьте `git status`. При чистом рабочем дереве можно использовать `git pull --ff-only`. Если команда отказала из-за расхождения веток, это защита от неявного слияния: не добавляйте `--force`, сначала посмотрите граф `git log --oneline --graph --all -15`.

## Запуск локально

```bash
cd ~/studiolink
pnpm install --frozen-lockfile
NEXT_BUILD_DIR=.next-dev STUDIOLINK_ROOMS_FILE="$PWD/apps/web/.studiolink-data/rooms.json" STUDIOLINK_STATS_DIR="$PWD/apps/web/.studiolink-data/stats" pnpm --filter web exec next dev -H 127.0.0.1 -p 3000
```

Команда остаётся работающей; открыть страницу нужно в браузере. Для медиа нужны согласованные настройки LiveKit в `apps/web/.env.local` и доступный LiveKit. Не копируйте сюда произвольные тестовые ключи поверх рабочих. Сам Next.js может запуститься даже при недоступном медиасервере.

Сборка и запуск именно этой сборки:

```bash
NEXT_BUILD_DIR=.next-local STUDIOLINK_RELEASE=local-manual pnpm --filter web build
NEXT_BUILD_DIR=.next-local STUDIOLINK_ROOMS_FILE="$PWD/apps/web/.studiolink-data/rooms.json" STUDIOLINK_STATS_DIR="$PWD/apps/web/.studiolink-data/stats" pnpm --filter web exec next start -H 127.0.0.1 -p 3000
```

Запускайте вторую команду только после успешной первой. Для проверки уведомления о новой версии используйте другой `STUDIOLINK_RELEASE` при следующей сборке. Не удаляйте каталог, из которого работает сервер. В задачах VS Code эти параметры уже заданы.

## Доступ к VPS и выпуск версии

Сейчас выбран локальный редактор, поэтому постоянный root-доступ редактору не нужен. Для просмотра сервера используйте отдельный терминал SSH. Проверки приведены в [диагностике](TROUBLESHOOTING_RU.md). При желании позже можно добавить [Remote SSH](https://code.visualstudio.com/docs/remote/ssh) под отдельным пользователем с ограниченными правами; такой доступ ещё не настроен.

Для выпуска: сначала коммит и проверенная сборка, затем резервная копия текущего образа, compose, конфигурации и данных на VPS; новый образ с уникальным тегом; изменение только web-сервиса; проверка `/api/version` и звонка двумя устройствами. Сохраните предыдущий тег для отката. Универсальную команду замены compose здесь намеренно не даём: полный серверный compose отсутствует в Git, его нужно сверять на VPS. `docker compose restart` не собирает изменённые исходники.

## Контекст сессий

В Issues храните дату, цель, затронутые файлы, коммиты, что проверено, что осталось, следующую команду. Это удобнее копирования всей переписки. Не добавляйте пароли, cookies, токены, `.env` и действующие приглашения. Issue является журналом для следующих сессий, но сам по себе не гарантирует, что новый инструмент автоматически прочитает его: дайте ссылку в начале работы.
