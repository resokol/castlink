# Приватный прототип атомарной остановки LiveKit при простое

Статус: исследовательский, выпуск заблокирован. Основа — upstream LiveKit v1.13.7, commit `8d11efdfcd4220092b6ac7b8a21af28526da5a6b`. Приватный patch не публикуется и не применяется на ПК/VPS пользователя. Четыре существующих сервиса сохраняются.

`TrySealIfIdle` должен одновременно проверить незавершённые `StartSession` и каждый созданный объект участника до подтверждённого завершения его транспортов. При занятости возвращается BUSY без изменения допуска, участников, сигналинга, данных и durable marker. Удаление из participant map, логический `Participant.Close`, JWT TTL, webhook и Prometheus gauge не доказывают завершение медиатранспортов.

Успешная операция закрывает допуск и сохраняет marker на приватном writable mount до возврата proof. Повторный запуск процесса в том же контейнере читает retained state и оставляет допуск закрытым; proof предыдущего процесса не восстанавливается. Proof связан с версией, digest образа, installation ID, точным container ID, operation epoch и process nonce. Новый контейнер не наследует подтверждение простоя предыдущего. Внешняя управляющая операция удерживает lease выбранной установки до конца lifecycle operation.

Управление предназначено исключительно для выделенного аутентифицированного listener на loopback контейнера и control subcommand того же бинарного файла через `docker exec`. Секрет передаётся через stdin или приватный файл; не через argv, URL, публичный порт 7880 или wildcard Caddy. Listener не публикуется наружу.

Неопределённое завершение транспортов, повреждённый marker, несовпадающие привязки и ошибки durable storage запрещают подтверждение простоя. В этом прототипе допустим sticky unknown: невозможность безопасно остановить предпочтительнее ложного разрешения, которое прервёт звонок.

До выпуска требуются независимое ревью, Go race проверки фактических upstream hook-путей, воспроизводимое применение pinned patch и сборка бинарного файла, реальная передача медиа при BUSY с сохранением связи, отказ допуска после seal, проверка терминального закрытия каждого транспорта, restart marker и замена контейнера. Одни тесты счётчиков и fake callbacks не закрывают эти критерии.

Ограничение первого этапа: любая ошибка конструктора `NewParticipant` сохраняет object ticket как UNKNOWN до конца процесса. Такой отказ не очищается TTL, повторным callback или автоматической перезагрузкой средствами этого прототипа. Constructor cleanup, включая hidden allocations Pion, не реализован. Правило согласовано архитектурным ревью Astra; частичные ресурсы не выдаются за завершённые.

Terminal helper сохраняет неблокирующий возврат проигравшего `PCTransport.Close`, отдельно ждёт завершения победителя и единственный cached `PeerConnection.GracefulClose`. Он вызывается из независимой cleanup goroutine, а не из Pion callbacks. Проверяются оба ненулевых PC; один зависший PC не мешает начать закрытие второго. Ошибка или timeout оставляет object ticket. Это MEDIA-terminal fence для закреплённых зависимостей; завершение всех вспомогательных goroutines не заявляется.

Private config читается по `CASTLINK_IDLE_SEAL_CONFIG` из обычного файла с правами 0600; секрет минимум 32 символа. Обязательные поля JSON: `binding` (`installationId`, полный `containerId`, `digest`, `version`), `stateDir`, `secret`. Текущая версия приватного control-контракта: `1.13.7+castlink-idleseal-private.2`. Runtime сверяет полный container ID с Docker hostname prefix. Controller отдельно проверяет фактический image digest, полный container ID и ассоциации установки, удерживая target lease. Самодекларация config не доказывает владение контейнером.

Субкоманда `livekit-server castlink-idle-control` принимает JSON через stdin: `operation` (`seal`/`unseal`), `epoch`, `binding`. Она читает management secret из private config и обращается только к `127.0.0.1:7889/control`, с отключённым HTTP proxy и без redirects. Порт 7889 не должен быть опубликован Docker/Caddy. При отсутствии private config upstream поведение сохраняется; такой экземпляр не предоставляет seal proof.

Историческая проверка исходного прототипа `d4ff961` до исправления ревью: финальный patch применён без ошибок к чистому upstream checkout закреплённого commit; focused Go race тесты `pkg/idleseal`, `pkg/rtc`, `cmd/server` и бинарная сборка прошли. Бинарный файл из авторского закреплённого source tree и файл из чистого checkout с применённым финальным patch совпали по SHA-256. В тестах использованы настоящие Pion PC и заблокированные transport event queues: duplicate Close возвращается, но терминальное ожидание сохраняет BUSY; оба PC начинают cleanup даже при зависшем первом; single-PC и обычный предшествующий Pion Close проверены. Полный upstream suite не запускался.

Исторический runtime proof до исправления ревью: изолированный cloud-контейнер с `--network none` и без опубликованных портов подтвердил аутентифицированную control-субкоманду, seal, сохранение marker через restart того же контейнера, отказ unseal с неверной эпохой и успешный bound unseal. Контейнер удалён после проверки. Найденная особенность upstream CLI — ошибка команды печатается при exit 0 — исправлена только для private control path: ошибка возвращает exit 1 и generic stderr, без success stdout. Client не принимает `200 OK` без связанного seal proof.

Непроверенные критерии: реальные resume/duplicate-identity гонки; детерминированная пауза внутреннего Pion Close; ошибка первого GracefulClose и её сохранение при повторных наблюдателях; все частичные constructor error paths; замена настоящего контейнера с прежним marker; независимое ревью текущих build/media evidence. Существующие unit-тесты container binding не заменяют последнюю runtime-проверку. Ни установка, ни update/stop, ни полный Task 8 не завершены.

Поддержка: patch и несекретная version-bound build/evidence metadata находятся в `infrastructure/livekit/private-idle-seal/`. `verify.sh` требует Go 1.26.0 и nonroot UID для реального directory-sync permission fault, создаёт собственный временный checkout, проверяет точный commit, patch, focused race тесты и сборку; он ничего не публикует и не меняет работающую установку. Прокси/CA на машине проверки должны быть настроены штатно, без отключения TLS verification. Для обновления upstream нужен новый source audit terminal/constructor paths и повторная проверка, а не перенос прежнего proof на другую версию.

Ревью обнаружило Important I1: после успешного unlink marker и ошибки directory fsync старый cached proof оставался доступен. Исправленный patch немедленно инвалидирует cached durability после unlink, до fsync; при ошибке допуск остаётся закрытым, а повторный `TrySealIfIdle` возвращает storage error. Настоящий filesystem fault при UID1000 (dir0300 разрешает unlink, запрещает directory open/fsync) дал RED со stale success, затем focused Go race GREEN. Test не подменяет storage mock и явно пропускается при UID0; verify.sh запрещает UID0, чтобы пропуск не выдавался за выполненное доказательство.

Историческая изолированная runtime-проверка private.1: два Chromium участника с синтетической камерой/микрофоном передавали настоящее WebRTC аудио и видео. При seal BUSY не появился marker/proof, сохранились connected identities и продолжили расти inbound bytes, outbound RTP packets и decoded video frames. После обычного SDK disconnect сначала наблюдались два BUSY, затем terminal seal; новое RTC подключение отклонено. Restart того же контейнера сохранил marker и proof, bound unseal вновь разрешил RTC подключение. Проверялся SDK harness, а не пользовательский UI приложения. Опубликованных Docker портов нет; собственные runtime/browser контейнеры и сеть удалены после проверки.

Настоящий отказ storage private.1 проверен в том же бинарнике при UID1000: state dir0300 допускает unlink, но не directory open/fsync. Unseal удалил marker, вернул ошибку без success stdout; следующий seal не выдал cached proof, новое RTC подключение осталось запрещённым в текущем процессе. Прерванный HTTP unseal проверен только до получения полного request body: marker/proof не изменились. Это не доказательство crash/power-loss после unlink. После неуспешного unseal marker отсутствует; сохранение sealed admission через последующий restart в таком состоянии не доказано и не заявляется. Lifecycle/controller не должен интерпретировать ошибку как разрешение stop/update.

Manifest содержит текущие private.2 build/runtime hashes и отдельно исторические private.1 proof. `Dockerfile.runtime` воспроизводит минимальный приватный runtime из заранее проверенного текущего бинарника с именем `livekit-server-private`; он не собирает исходники и не публикует образ. Выпуск, SafeStop и lifecycle integration по-прежнему заблокированы.

Исправление private.2 меняет restart-контракт: каждый процесс начинает с закрытым допуском и новым криптографическим `processNonce`. Прежний proof после restart недействителен, даже в том же контейнере. Каждая seal/unseal команда содержит текущий nonce; аутентифицированный `status` получает его без изменения состояния. Proof содержит nonce. Controller под target lease может открыть допуск только новым seal с ещё не использованной эпохой, затем unseal этого proof. Непрерывность автоматического запуска без оператора **UNVERIFIED**: bootstrap controller пока не реализован; это ограничение прототипа, не завершённая замена независимого autostart.

Runtime `Open` требует существующие `state.json` schema2 и sibling anchor `<stateDir>.initialized`, связанные с точным binding. Missing/corrupt/mismatched/legacy state не создаётся автоматически и запрещает запуск. Отдельная offline команда `castlink-idle-initialize` создаёт только новый state directory и exclusive durable anchor; повторный init, даже после удаления directory при сохранённом anchor, запрещён. Partial init сохраняет blocker. Удаление или сброс anchor/state средствами прототипа не предусмотрены.

Durable record содержит `sealed` или `retired`, active epoch и полный bounded set использованных opaque epochs. Seal сохраняет epoch до выдачи proof. Только active proof того же процесса можно наблюдать повторно. Unseal сначала сохраняет `retired` через file fsync/rename/directory fsync и только после успеха открывает допуск **в памяти**. Durable OPEN записи нет: даже читаемый final record после failed directory fsync при restart не разрешает admission. Ошибка оставляет текущий процесс закрытым без proof; old nonce/epoch не переиспользуются. Лимиты128 использованных эпох и65536 сериализованных state bytes — availability limitation (JSON escaping может исчерпать byte budget раньше); при исчерпании выдача нового proof запрещена, tombstones не удаляются.

Focused nonroot race tests воспроизвели RED для fault→restart admission, повторной эпохи после успешного unseal, missing retained state и reset после удаления state directory. Исправление дало GREEN; actual dir0300 допускает final rename, но запрещает directory open/fsync. Terminal/session production hooks не изменены. Новый private.2 бинарник и targeted container restart proof пройдены ниже; прошлый binary198e/imageD8 не соответствуют новому patch. Выпуск и functionalStop заблокированы.
