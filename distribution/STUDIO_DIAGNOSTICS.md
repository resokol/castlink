# Диагностика основной студии

[English](docs/en/STUDIO_DIAGNOSTICS.md) · [简体中文](docs/zh-CN/STUDIO_DIAGNOSTICS.md)

## Когда прерывается звук или замирает видео

В основной студии откройте **Статистика**, выберите комнату и период, в который попал сбой. Для первого разбора оставьте все роли, всех участников и все сессии. Запишите время с часовым поясом, чей поток пострадал и кто заметил проблему. Участникам ничего нажимать не требуется.

Введите местное время в поле **Минута сбоя** и нажмите **Разобрать минуту**. Сопоставьте один трек у отправителя и каждого приёмника, пики потерь и покрытие пятисекундных интервалов. Таблица доступности показывает состояния соединения и прирост переподключений между замерами одной сессии. Результат и исходные замеры за эту же минуту сохраняет **Скачать диагностику этой минуты**.

У администратора платформы в этом представлении также видны проверки API LiveKit и количество принятых и пересланных ключевых кадров по всем комнатам ноды за каждый измеренный интервал. Один входной кадр может быть переслан нескольким получателям. Сбор выполняется в фоне примерно раз в 15 секунд, история ноды хранится до 24 часов. После перезапуска, при пропуске или отсутствии счётчика значение остаётся пустым. Для стандартного LiveKit 1.13.11 в закрытой сети Docker Compose администратор может подключить `infrastructure/production/compose.incident-metrics.bridge.yml` как дополнительный файл действующего bridge-проекта. Установка сохраняет текущие файлы Compose и публикуемые порты. При host networking этот шаблон применять нельзя.

1. Нажмите **Разобрать проблемы связи**. Найдите эпизод по времени и источнику, посмотрите показатели и предложенное действие. Прямое наблюдение бывает, например, когда браузер отправителя сообщил об ограничении кодирования по CPU. Вероятную причину CastLink выводит из сравнения одного потока у нескольких получателей. Если данных мало, сторона сбоя остаётся неизвестной. Выбор одного получателя может убрать из сравнения остальные точки наблюдения.
2. Если один и тот же поток замирал у нескольких получателей одновременно, проверьте отправителя и общий путь доставки. Совпадение по времени ещё не указывает на неисправность сервера. История LiveKit, когда она доступна, подтверждает наличие публикации и состояние mute в момент опроса. Для измерения потерь нужны отчёты медиасоединения. Отдельный маршрутизатор или провайдер по этим данным может остаться неизвестным.
3. Нажмите **Скачать полную диагностику** с теми же фильтрами. Браузер сохранит файл NDJSON. Первая строка `manifest` содержит границы выборки, далее идут замеры клиентов и доступные наблюдения LiveKit. Последняя строка `summary` содержит выводы и признак `complete`. Если этой строки нет или `complete: false`, выгрузка неполна. Даже при `complete: true` возможны промежутки, когда замеры не поступали. Передайте файл специалисту вместе со временем и описанием сбоя.

Администратору платформы выгрузка также даёт строки `server-load-sample` с исходными замерами CPU узла. Если высокая нагрузка совпала по времени с эпизодом, проверьте процессы узла в этот момент. Одного совпадения недостаточно, чтобы отнести сбой к LiveKit.

Разбор и выгрузка читают сохранённую историю по запросу. Файл передаётся частями. Во время эфира короткий период вокруг известного эпизода ускоряет обработку.

В сборках с этим исправлением шкалы громкости обновляются в своих компонентах. Обновление шкал больше не обновляет список участников на каждом кадре.

После обновления сервера заново откройте основную студию в браузере или Windows Client. Во вкладке **Статистика** раскройте **Диагностика основной студии**. Последние полученные данные обновляются вместе со статистикой примерно каждые15секунд; сервер получает замеры примерно каждые2секунды. При отсутствии свежих замеров отображается предупреждение.

Доступны состояние видимости вкладки, задержка её основного потока и максимум с начала сессии, счётчики ошибок JavaScript и rejected promises, доступные браузеру память JavaScript и длительные задачи. Недоступное API означает отсутствие значения, а не нулевую нагрузку. Фоновое ограничение таймеров не считается зависанием видимого интерфейса. Память JavaScript — не вся память вкладки и не GPU.

**Диагностика студии → JSON** скачивает историю с выбранными периодом/днём/участником/сессией. Для основной студии выберите роль «Студия». Лимит выгрузки —50000замеров или20МиБ; неполный файл отмечается как partial. Просмотр доступен владельцу студии/администратору комнаты, платформенная история — действующему super-admin.

**Журнал этой вкладки → JSON** работает независимо от сервера статистики. Вкладка хранит ограниченный снимок текущей и предыдущей сессии в sessionStorage, обычно раз в10секунд и при изменении видимости/завершении. После перезагрузки страницы предыдущая запись сохраняется в той же вкладке, если браузер разрешает хранилище. Закрытие вкладки может удалить журнал. Нужна исходная вкладка и тот же origin. Хранилище недоступно — сбор/экспорт текущих доступных данных продолжает работать в памяти.

Сервер сохраняет диагностику в существующие hourly JSONL-файлы: `${STUDIOLINK_STATS_DIR}` либо `${STUDIOLINK_DATA_DIR}/stats/<room-hash>/<hour>.jsonl`; старые часы сжимаются в `.jsonl.gz`. Умолчания:30дней и общий лимит512МиБ. Лимит диска может сократить период. Существующие безопасные ошибки браузера отмечаются `browser.crash` в журнале web-службы (`docker logs` или штатный журнал установки). Не публикуйте весь серверный журнал без проверки его содержимого.

Новые runtime-поля не содержат запись медиа, пароли, токены, полные URL, имена устройств или произвольный текст ошибок. Выгрузка серверной статистики содержит существующие имена/идентификаторы участников; передавайте её только тем, кто разбирает инцидент.

Полный сбой renderer/GPU или завершение процесса может не оставить последней записи. Пропуски замеров и последние показатели помогают сузить причину, но не доказывают её. После сбоя скачайте серверный JSON за время инцидента и локальный журнал той же вкладки, укажите время и вид экрана.

Timeweb обновляется отдельно от самостоятельных серверов. Установка новых Windows/Linux серверных пакетов нужна для других установок; обновление одного Client EXE не обновляет их серверный код. Клиент, открывающий уже обновлённый сервер, получает новую веб-студию после перезагрузки.

## Диагностика звука

В сборках с расширенной аудиодиагностикой CSV аудиоистории отдельно показывает mute публикации, SDK-трека, нативного MediaStreamTrack и элемента воспроизведения. `Muted элемента воспроизведения` — прежняя колонка `Muted`; она не говорит, выключен ли микрофон кастера. Порядок прежних колонок сохранён, новые добавлены справа.

Для исходящего звука записываются доступные фактические частота дискретизации, число каналов, NS/AEC/AGC/voice isolation и уровень связанного media-source. Имена и идентификаторы устройств не собираются. Для входящего звука добавлены накопленные и интервальные счётчики silentConcealedSamples, вставленных и удалённых samples при коррекции темпа. Эти значения помогают отличить подставленную тишину от восстановления речи и изменения темпа; сами по себе они не устанавливают причину слышимого искажения.

100% Concealed не означает 100% сетевых потерь: при выключенной публикации приёмник может продолжать выдавать подставленную тишину. Сопоставляйте mute отправителя, поступление RTP, уровень источника и других получателей. Недоступные браузеру значения и старые записи остаются пустыми. Если RTP-статистика трека недоступна, этих полей тоже может не быть. Новые поля появляются только после обновления сервера и страниц отправителей/получателей вне эфира; старую историю они не дополняют. Автоматического перезапуска или включения микрофона нет.

Файл с `partial` содержит только часть выбранного периода, начиная с ранних записей; поздний инцидент может отсутствовать. Проверьте последнюю отметку времени, выберите более короткий текущий период либо отдельного участника/сессию. Для произвольного исторического интервала оператор может прочитать сохранённые hourly-файлы или штатный авторизованный API с фиксированными `to`, `minutes` и последовательным `cursor`.
